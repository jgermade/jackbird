# Session: Musikmatch — Rust core, multi-source library, vfs-sync integration

**Date**: 2026-08-11 20:34
**Summary**: Rename the project to Musikmatch, move the core to Rust (axum/tokio/sqlx/rodio/symphonia/lofty),
restructure `.meta` into per-track sidecars with a content-addressed image store, and adopt
`@cloudauthn/vfs-sync` as the synchronisation layer across multiple sources.

**Status**: Proposal — awaiting approval. No code changed yet.

---

## 1. Context

The project is today a zero-backend browser app (React 18 + Vite + TypeScript) that edits ID3 tags
in place through the File System Access API. Two documents describe it: [STACK.md](../STACK.md) and
[THESAURUS.md](../THESAURUS.md).

It becomes **Musikmatch**: a music player *and* a file organiser/renamer, running on web, desktop
and mobile, over several storage sources that can be synchronised with each other.

### What the audit found in the current `.meta` implementation

Reviewed in [Mp3ManagerView.tsx](../src/views/Mp3ManagerView.tsx) and [id3.ts](../src/lib/id3.ts).

Worth keeping:

- Dual checksums (`fullChecksum` over the whole file, `audioChecksum` over the audio payload with
  ID3v2/ID3v1/APE stripped) — `getAudioFrameSlice` / `calculateDualChecksums`, id3.ts:113-175.
- Fast re-hydration validated by `(size, lastModified)` without reading bytes.
- Two-phase hydration: render from the snapshot first, walk the filesystem in the background.

Must change:

1. **Cover art is base64 inside the JSON.** `MetaRecord.metadata` carries the full `TrackMetadata`
   including `coverDataUrl`. At ~700 tracks this is a multi-hundred-MB file, re-serialised whole
   (`JSON.stringify(snapshot, null, 2)`) every 10 verified files (Mp3ManagerView.tsx:341-343).
2. **The primary key is `relativePath`**, in an app whose purpose is renaming files. A rename
   discards the record, including the `audioChecksum` that exists precisely to be rename-stable.
3. **Three uncoordinated writers** to the same file — the background verifier mutating a captured
   snapshot in place (L290-343), phase 2 of `hydrateRoot`, and batch edit (L1177-1182). Last writer
   wins over the entire library.
4. **O(n) rewrite per change.**
5. **`version !== 1` silently yields an empty snapshot** (L1503) and then overwrites the file. A
   future v2 opened by an old build destroys the library.
6. **`VfsAdapter` is decorative.** Its only consumer is the `implements` clause in
   [browserVfs.ts:14](../src/vfs/browserVfs.ts#L14); the view is typed against the concrete
   `BrowserVfs` and uses six methods absent from the interface (`mountFromHandle`,
   `hasReadWritePermission`, `getRootHandle`, `getRootName`, `readTextFile`, `writeTextFile`).
7. **Unstable file ids.** `${relativePath}#${lastModified}#${size}` (browserVfs.ts:188) changes
   exactly when the file changes, which is why phase 2 has to patch `vfsFileId` after the walk.

## 2. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | Rust core: tokio, axum, sqlx/SQLite, symphonia, rodio, **lofty** | symphonia cannot write tags; lofty reads *and* writes ID3v2/MP4/FLAC/Vorbis plus artwork |
| D2 | Multi-format from day one; `Mp3Track` → `Track` | lofty and symphonia make it nearly free |
| D3 | Zero-install web mode survives | Cloud sources are HTTPS+CORS from the browser; the daemon becomes *one source among several*, not a requirement |
| D4 | MusicBrainz/AcoustID: reserve schema fields now, build matching later | `mbid_recording`, `mbid_release`, `acoustid` are free to reserve, expensive to retrofit onto synced replicas |
| D5 | One tag engine everywhere: lofty compiled to wasm for browser sources | If the browser wrote ID3 with `browser-id3-writer` and desktop with lofty, byte output would differ, hashes would never match and sync would loop. This is a correctness requirement, not an optimisation |
| D6 | `@cloudauthn/vfs-sync` stays **TypeScript only** for now | Owner's call. Consequence: the sync engine runs in the JS layer on all targets (Tauri's frontend is JS) |
| D7 | SHA-256 everywhere; **drop blake3** | vfs-sync content-addresses with SHA-256. Reusing it means `full_hash` comes free from the tree entry and image filenames equal the engine's blob address |
| D8 | Two views: Player and Organiser | The Player is read-only over the index and needs no write permission on any source — which is what makes iOS viable. Organiser ships on desktop and web only |
| D9 | Canonical tags live in `.meta`; writing them into the audio files is an explicit apply/export | See §5 — this is what keeps the sync engine's two missing features from mattering |

### Deferred / open

- **O1**: whether vfs-sync eventually collapses to a single Rust implementation compiled to wasm
  (zero drift, one engine) or keeps a dual TS+Rust implementation (needs a versioned `.vfs/` spec
  and a shared conformance suite). D6 defers this; it does not settle it.
- **O2**: album key. MusicBrainz release MBID when known; otherwise a generated UUID stored in the
  record. **Not** a hash of (album_artist, album, year) — that changes when a typo is corrected.
- **O3**: default policy for keeping artwork embedded in the audio files (proposed default: keep
  embedded, with `.meta/images/` as the canonical store).

## 3. Target architecture

```
crates/
  core/     domain: Track, Album, identity, rename rules. No I/O.
  tags/     lofty — read/write tags and artwork over bytes. Compiles to wasm.
  index/    sqlx + SQLite: schema, migrations, queries.
  scan/     walk + (size, mtime) fast path + hashing + notify.
  audio/    symphonia (decode, duration) + rodio (native output).
  server/   axum — same handlers behind every transport.
apps/
  desktop/  Tauri v2, reuses the React UI.
  mobile/   Tauri v2 iOS/Android — Player only.
  web/      React UI; sources are FSA/OPFS/Drive directly, or the daemon over HTTP.
```

### The storage seam

`VfsAdapter` is replaced by an **operations** interface rather than a bytes interface. Shipping
whole files across an IPC or HTTP boundary just to hash or tag them is strictly worse than what
exists today.

```rust
#[async_trait]
pub trait StorageBackend: Send + Sync {
    async fn scan(&self, opts: ScanOpts) -> Result<Vec<FileStat>>;
    async fn hash(&self, id: &FileId) -> Result<Hashes>;        // full + audio
    async fn read_tags(&self, id: &FileId) -> Result<Tags>;
    async fn write_tags(&self, id: &FileId, tags: &Tags) -> Result<()>;
    async fn rename(&self, id: &FileId, to: &RelPath) -> Result<FileId>;
    async fn open_stream(&self, id: &FileId, range: Range) -> Result<ByteStream>;
    async fn watch(&self) -> Result<Receiver<FsEvent>>;
}
```

`FileId` stays opaque and, unlike today, **stable** — Android SAF hands out content URIs and iOS
security-scoped bookmarks, so paths are not universal identifiers.

### The JS/Rust boundary

- **JS owns**: FSA/OPFS handle management, the directory picker, permission prompts, byte read and
  write. Roughly what [browserVfs.ts](../src/vfs/browserVfs.ts) already is.
- **wasm (Rust) owns**: tag parse/write, hashing, audio-payload slicing, rename rules.
- **Native Rust owns**: the same crates plus the real filesystem, cloud clients, rodio/symphonia.

The index is the one component genuinely written twice: sqlx does not compile to wasm. Proposal —
SQLite in the browser via wa-sqlite over OPFS, with schema, migrations and queries kept as shared
SQL text and two thin drivers.

## 4. `.meta` format

```
.meta/
├── tracks/<audio_sha256>.json       # tags, current path, uuid, mbids, full_hash
├── albums/<album_key>.json          # album_artist, year, images[]
├── artists/<artist_key>.json        # images[]
├── images/<sha256>.<role>.<ext>     # content-addressed, deduplicated
└── library.json                     # root settings, schema version
.vfs/                                # sync state, owned by vfs-sync
```

**Per-track sidecars are mandatory, not a preference.** A single JSON plus a file-level syncer means
one conflict takes the whole library; split per track, the worst case is a conflict copy of one song.

**Sidecars are named by content, not by path.** If the sidecar were path-named, renaming the audio
on peer A while editing tags on peer B is a rename-vs-edit conflict on one file. With an immutable
name, renaming is just editing a field in a small JSON. Deduplication comes free. The 1:1 reflection
of audio files in `.meta` is preserved — it is logical (one record per audio) rather than positional
(the tree shape is not mirrored).

**Torn renames self-heal.** A rename touches two things (the audio file's name, the `path` field in
its sidecar), so a peer can observe an inconsistent state. No transactional support is needed from
vfs-sync: the tree entry `id` says the file moved and `audio_sha256` says which record it belongs
to, so reconciliation needs no re-hashing.

### Images

Role in the filename, as requested: `images/<sha256>.front.jpg`.

- The `<sha256>` prefix **is** the identity, and equals the vfs-sync blob address (D7).
- The role suffix is a **non-authoritative hint** for human browsing. The record is the source of
  truth. Where an image holds several roles, the suffix is picked by a fixed precedence
  (`front > back > disc > booklet > artist > label`) so every peer derives the same name.
- If two peers do write the same bytes under different suffixes, vfs-sync stores and transfers
  **one blob** — the cost is a second working-folder file, reconciled by app-level GC, not a second
  transfer.
- The suffix token must be spelled exactly like the role in the record, so hint and truth cannot
  disagree. Vocabulary follows the MusicBrainz Cover Art Archive (`front`, `back`, `disc`,
  `booklet`, `artist`, `label`), which also maps ~1:1 onto the ID3 APIC picture-type byte, making
  extraction lossless. **Note**: this replaces the `cover` token from the original sketch —
  `front` is the CAA term.
- Records carry `images: [{ hash, role, mime, w, h }]`.

Album- and artist-level records exist because a back cover belongs to a release and a photo to an
artist. Hanging them off track sidecars would have twelve songs each claiming the same artwork,
turning every artwork edit into a twelve-way conflict.

### Identity: two layers, both needed

- **vfs-sync `id`** — identity of a *file in the mesh*. Survives renames; this is what stops a moved
  album from re-transferring.
- **`audio_sha256`** — identity of the *musical content*. Survives retagging and renaming, and —
  which the mesh id cannot do — identifies the same recording arriving at two sources by independent
  paths, having never synced. Without it there is no dedup and no library merge.

`full_hash` is not computed by Musikmatch at all: it is the vfs-sync tree entry's `hash` (D7).

## 5. vfs-sync

Reviewed at `.tmp/vfs-sync` (v0.1.21, MIT). It is a git-shaped engine: SHA-256 content-addressed
blobs, tree snapshots, commits with parents, real ancestor negotiation, mesh topology, tombstones,
rename intent carried in the tree, logical mtime, conflict copies. Adapters: OPFS, FSA, Google
Drive, Node fs, Memory.

Consequences for the design above:

- **Ancestor bookkeeping is not our problem.** Earlier in this design I planned to record
  per-replica `last_synced_*` state; the engine's commit graph already does it. Do not duplicate it.
- `readRange` already exists, and its doc comment cites this exact use case ("parse the ID3 tag of
  a 200 MB track" for a few hundred bytes).
- Blob dedup across paths and peers is already there, which is what makes the image naming scheme
  cheap.

### Layering invariant

vfs-sync's scope is *N peer folders, content-agnostic*, and that must hold. **Test: if vfs-sync ever
needs to know what an MP3 is, the layering is wrong.** `.meta/` is, to the engine, an ordinary
folder of files it does not interpret.

### Proposed contributions (all content-agnostic)

Ordered by value to Musikmatch. Following the codebase's existing convention: optional adapter
methods with emulated fallbacks, as `fileId?()` and the streaming trio already do.

1. **Garbage collection.** Listed under "Not implemented" in `docs/architecture.md`; unreachable
   blobs are never removed. For a music library this is acute — every tag write rewrites the whole
   file, minting a new blob and orphaning the old one. A 200 GB library retagged twice would carry
   ~600 GB of `objects/`.
2. **Selective materialisation** — letting a peer hold a file's metadata without its content. This
   is what makes mobile viable: sync `.meta/` in full, browse a 200 GB library, fetch bytes on
   demand. Generic (Dropbox smart sync), and it unlocks a whole target.
3. **Delta transfer.** Also listed as not implemented: a one-byte change re-sends the whole file.
   Because ID3v2 sits at the head of the file, a tag edit shifts everything after it, so
   content-defined chunking (FastCDC) suits this better than fixed-block rsync.
4. **Backend-native transfer fast path.** When both peers share a backend, skip streaming through
   the engine — Drive→Drive is an API call with zero bytes on the wire.
5. **A resolver hook on `sync()`.** `mergeTrees` is pure and exported, but the documented recipe for
   custom resolution requires supplying your own `commonAncestorTree` — i.e. reimplementing the
   hardest part of the engine. A hook (by path pattern or mime) would let Musikmatch register
   per-field JSON merging for sidecars without leaving the engine, and would keep music semantics
   out of vfs-sync.
6. **Native digest passthrough** — Drive `md5Checksum`, Box `sha1`, Dropbox `content_hash`, to
   compare without downloading. Caveat: algorithms differ per provider, so it must be treated as an
   opaque digest comparable **only within one backend**, never across two.

### Why D9 matters

Items 1 and 3 above are the sync engine's two known gaps, and both are triggered by the same thing:
rewriting a 10 MB audio file to change 20 bytes of tag. Keeping canonical tags in `.meta` and making
"write tags into the audio files" an explicit operation means the audio blobs stop churning during
normal editing — which demotes both gaps from blocking to merely desirable.

## Extension — 2026-08-11 21:05 — Open questions closed, in-file identity model

Resolves O1, O2 and O3, and adds D10: what may and may not be written into the audio files.

### O2 — Album key: generated UUID

Minted once, stored in the album record. Never derived from `(album_artist, album, year)`, which
changes when a typo is fixed. MusicBrainz release MBID recorded alongside it when known, as an
attribute rather than as the key.

### O3 — `.meta/images/` is a mirror of what the audio file carries

Decided: the extracted image is byte-identical to the embedded APIC payload. **Supersedes the
downscaled-thumbnail proposal** — no derived renditions, no divergence between what the file has
and what `.meta` shows.

Consequences:

- The audio file stays the source of truth for its own artwork; `.meta/images/` is a faithful,
  rebuildable projection of it.
- The role suffix comes straight from the APIC picture-type byte, so extraction is lossless in
  both directions.
- Deduplication still holds: the same artwork embedded in twelve tracks yields twelve identical
  payloads, one SHA-256, one file.
- Because it is derivable, `.meta/images/` is technically a cache — but it must still be synced,
  since a peer holding metadata without content (selective materialisation, §5 item 2) has no
  audio files to project it from. This is what lets a phone show covers for a library whose bytes
  it does not hold.
- Accepted cost: changing artwork rewrites every affected audio file. Mitigated by D9 — the
  rewrite happens on apply, not on every edit in the UI.

### O1 — Dual implementation, TS + Rust, with a versioned spec

Decided. The `.vfs/` on-disk format and the engine's semantics become a public contract between two
codebases; divergence causes silent data loss rather than an error, so the spec and a **shared
conformance suite** are the real deliverables, not the second implementation.

Every rule the docs describe as "deterministic so both peers compute it identically" is a
conformance hazard and must be pinned down in the spec:

| Area | What must match exactly |
| --- | --- |
| Trees | Canonical JSON encoding, entries sorted by `id` |
| Hashing | SHA-256, and precisely which bytes are covered |
| Identity | The five-step id resolution order (rename intent → path continuity → hash heuristic → hash cache → fresh id) |
| First encounter | Fall back to path matching; lexicographically smaller id wins |
| `storeId` | Both peers adopt the lexicographically smaller |
| Merge | Per-dimension resolution, newer `mtime` wins, hash tiebreak |
| Conflict copies | Name derived from content, so repeated merges produce the same path and id |
| Ancestor | Frontier computation, ordered by timestamp then hash |

Suite shape: scenario fixtures in a language-neutral format (initial state of N peers, operations,
expected converged tree and commit hash) executed by both implementations, plus property tests
generating random operation sequences and asserting that all peers converge with no data loss.

### D10 — What goes in the audio file

The earlier ruling ("no sync information in ID3") was drawn too broadly. The real dividing line is
not ID3-versus-sidecar, it is **peer-invariant versus peer-specific**.

- **Peer-invariant** data converges: every replica ends up with identical bytes. It can live in the
  file.
- **Peer-specific** data cannot, by construction. "Last synced with peer X at T" has three
  different values across three peers for one shared object. Its home is `.vfs/`.

`fileHash` additionally cannot be stored in its own file — writing it changes the bytes it
describes. `audioHash` can: it covers only the audio payload, so a tag write leaves it valid. It is
a fixed point under retagging.

Adopting the XMP Media Management model, which solves this exact problem for images and PDFs:

| Frame (`TXXX` / `UFID`, owner `musikmatch`) | XMP analogue | Written | Purpose |
| --- | --- | --- | --- |
| `track_id` | `xmpMM:DocumentID` | Once, at import | Identity across retag and rename |
| `origin_id` | `xmpMM:OriginalDocumentID` | On derivation | Lineage when `audioHash` breaks — transcode, normalise, re-encode |
| `rev_id` | `xmpMM:InstanceID` | Every write | Identifies this byte state without being a function of it |
| `audio_sha256` | — | Every write | Content identity; precedent: Picard stores `Acoustid Fingerprint` the same way |

`rev_id` is what the "hash of the last sync" idea was reaching for. A file cannot contain its own
hash, but it can contain a token minted at write time that serves the same purpose. Comparing it
against the index distinguishes three cases vfs-sync alone cannot:

- **Same `rev_id`** — untouched, whatever the filesystem timestamps say.
- **Different but known `rev_id`** — edited by another Musikmatch peer.
- **Missing or unknown `rev_id`** — edited by a foreign tool (iTunes, Picard, a car stereo).

Cost rule: none of these ever trigger a write on their own. They piggyback on writes already
happening — import, or applying tags — so they add no churn. On read-only or write-expensive
sources they are simply skipped, and `audio_sha256` still covers the normal case.

References: [XMP Media Management namespace](https://developer.adobe.com/xmp/docs/xmp-namespaces/xmp-mm/),
[Picard ID3 formats](https://github.com/metabrainz/picard/blob/master/picard/formats/id3.py).

## Extension — 2026-08-11 21:40 — Ignore rules

Adds contribution 7 to §5, plus a data-loss bug that must be fixed before any of it.

### What already exists

`VFSNode.open(adapter, { ignore })` takes a predicate (`WalkOptions.ignore`, walk.ts:11), and
`docs/recipes.md` already sketches reading patterns from a `.vfsignore`. The mechanism is there;
what is missing is a file format and the fix below.

### Prerequisite bug: ignoring a tracked file deletes it across the mesh

`scan()` derives what disappeared from the paths the walk returned, and the walk applies `ignore`:

```ts
const files = await walk(this.adapter, this.ignore ? { ignore: this.ignore } : {});  // vfs-node.ts:193
const vanished = prevLive.filter((e) => !livePaths.has(e.path));                      // vfs-node.ts:228
```

So a file that was already tracked and then becomes ignored is indistinguishable from a deleted
one: it enters `vanished`, gets a tombstone, and the tombstone propagates and removes it on every
peer. `docs/recipes.md` states ignored paths "never appear as deletes on the other side", which
holds only for paths that were *never* tracked.

Fix: "not walked" and "not present" must be different things — `scan()` must exclude currently
ignored paths from the `vanished` computation and leave their entries untouched. Git solves the
same problem by refusing to ignore already-tracked files. This is a prerequisite for any
file-based rule format, which makes the mistake trivially easy to trigger.

### Where the rules live

Two mechanisms, split the way git splits `.gitignore` from `.git/info/exclude`. Location does not
change *what* the rules govern — always the working folder — only whether the rules themselves
travel between peers, since everything under the control dir is skipped by the walk
(walk.ts:26).

| | Home | Travels? | Format | Written by |
| --- | --- | --- | --- | --- |
| Shared | `.vfsignore`, working folder | Yes — it is ordinary synced content | Plain text, `#` comments | Hand or app |
| Local | `ignore?: string[]` in `.vfs/config.json` | No | JSON array | Engine only, via API |

The local half goes into `config.json` rather than a separate `.vfs/ignore`: `NodeConfig` already
evolves by optional field (`storeId?` — "Absent only in stores written before it existed"), and one
less file in the control dir is one less round trip per `open()`, which on Drive is what walking
costs. The tradeoff is that `config.json` is engine-written on every commit and sync, so hand
editing races with it — acceptable precisely because these rules are set through the API, not by
hand. A separate file would only earn its place if hand-editing were a supported workflow.

### What Musikmatch actually needs

**Only the local half, at first.** Every peer runs Musikmatch and ships the same default rules for
OS junk (`.DS_Store`, `Thumbs.db`, `._*`, `@eaDir`, `.Trashes`), so the app binary already
guarantees the symmetry that a shared file would otherwise provide. `.vfsignore` is the
general-case feature — heterogeneous peers, user-authored rules — and belongs in vfs-sync without
Musikmatch depending on it on day one.

Residual risk: version skew. If one peer ships a rule another lacks, the docs' asymmetry hazard
applies ("the ignoring peer receives the file but never reports it"). Confined to junk files, so
low stakes, and the tombstone fix keeps it from turning into data loss.

`.meta/` must never appear in any rule set — it is the metadata plane and has to sync in full.

### Not to be confused with selective materialisation

Opposite mechanisms. Ignoring makes a file invisible to the tree; materialisation (§5 item 2)
keeps it in the tree without holding its bytes. "Sync `.meta` to the phone but not the audio" is
materialisation — ignoring would leave the phone with a tree in which the tracks do not exist, and
therefore nothing to display.

### Bootstrap ordering

A shared `.vfsignore` is itself content, so the sync that delivers new rules still runs under the
old ones. It converges on the second pass, which `syncUntilStable` already provides.

## Extension — 2026-08-11 21:52 — Ignore: both mechanisms adopted

Supersedes "What Musikmatch actually needs" above, which proposed deferring the shared half.

`.vfs/ignore` is dropped — it was only ever shorthand for the idea. The arrangement is:

- **`.vfsignore`**, working folder, synced, plain text with `#` comments.
- **`ignore?: string[]`** in `.vfs/config.json`, local, set through the API.

Both are adopted from the start, not just the local one.

### Composition

The engine reads both at `open()` and composes them into the single predicate the walk already
takes. **Union**: a path ignored by either is ignored, exactly as git applies `.gitignore` and
`info/exclude` together. No precedence to define, because there is nothing to break a tie between.

That holds only while there is no negation. If `!pattern` un-ignore rules are ever added, order
becomes observable and has to be specified — last match wins within a file, and one file has to be
declared to outrank the other. Recommendation: ship without negation and keep union.

### Pattern syntax

Full gitignore semantics (leading `/`, trailing `/`, `**`, `!`, nested files that re-scope) is a
large surface for what this needs. Minimal subset that covers every real case:

| Form | Matches | Example |
| --- | --- | --- |
| exact path | that path | `docs/notes.md` |
| directory prefix | the subtree | `.cache/` |
| `*` glob on the basename | any directory | `*.tmp`, `.DS_Store` |

Any of the three matched anywhere in the tree, since OS junk appears at every level — `.DS_Store`
must match in all folders, not only the root.

### `.vfsignore` is not self-ignorable

It is ordinary synced content and the mesh needs it to converge, so the engine must refuse to let a
rule exclude it — the same way git always tracks `.gitignore`. Otherwise one peer can drop the
rule set out of the tree and the others read it as a delete.

the other is the one D9 addresses. The decision stands; its justification narrows.

### The seam M0 adopts

`VFSAdapter` in 0.2.0 is **path-based**, not operations-based:

```
list / read / write / delete / rename / stat                    required
mkdir / fileId / readRange / readStream / writeStream / append  optional
changes                                                          optional
```

That is the opposite shape from §3's `StorageBackend` (opaque `FileId`, `hash` and `read_tags` as
operations). The two answer different questions rather than conflicting:

- **vfs-sync's `VFSAdapter` is the transport seam.** It exists, is tested, and is what the sync engine
  consumes. Every backend the plan wants already implements it — FSA, OPFS, Drive, node — and
  `FSAAdapter` ships `pick`, `fromHandle`, `hasPermission` and `ensurePermission`, which is precisely
  the surface `Mp3ManagerView` uses and `VfsAdapter` never declared.
- **`StorageBackend` remains the Rust-side seam** for M2, where a whole-file round trip across HTTP
  genuinely is the cost to avoid. It is not what the TypeScript UI talks to.

Why adopt the engine's interface at M0 instead of inventing a local one now and replacing it at M3:
one seam, validated by the code that will actually use it, and nothing written to be thrown away. It
also pulls the dependency in earlier than M3 — the milestone that read "integrate vfs-sync" becomes
"wire the mesh", which is the smaller of the two.

4. Call-site map, all inside `Mp3ManagerView.tsx`:

| Today | After |
| --- | --- |
