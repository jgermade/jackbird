# ROM Manager Template Cleanup

Context: `.tmp/rom-manager` is a symlink to a sibling project (`wasm-gaming/rom-manager`)
used as a reference template when mp3-manager was bootstrapped. A deep review against
it surfaced several leftovers and gaps. User approved proceeding with all of them
("adelante con todo").

## Findings

1. **Bug (user-visible)**: [src/views/Mp3ManagerView.tsx](../src/views/Mp3ManagerView.tsx)
   still renders `<h1 className="brand">ROM Manager</h1>` — leftover branding from the
   template this project was bootstrapped from.
2. **Stale docs**: [STACK.md](../STACK.md) is byte-identical to rom-manager's `STACK.md`
   (Preact, preact-router, MiSTer systems, DAT matching, tsup, oxlint, vitest — none of
   which apply here). It must describe the real stack (React, Vite, jsmediatags,
   browser-id3-writer, VFS abstraction).
3. **Broken reference**: [AGENTS.md](../AGENTS.md) links to `THESAURUS.md`, which does not
   exist in this repo.
4. **Committed build artifacts**: every `.ts`/`.tsx` file under `src/` has a compiled `.js`
   twin (e.g. `src/components/RootTabs.js`), produced by `tsc -b` emitting because
   `tsconfig.json` has no `"noEmit": true` / `outDir`. These are stale (some still say
   "ROM Manager") and pollute the source tree.
5. **UI/architecture gap vs rom-manager**: no theming (dark/light), no i18n layer, no
   `services/`/`core/` split — everything lives in one large view
   (`Mp3ManagerView.tsx`) plus `lib/`/`vfs/`.

## Plan

1. Fix the "ROM Manager" → "MP3 Manager" branding bug in `Mp3ManagerView.tsx`.
2. Delete all committed compiled `.js` twins under `src/`; add `"noEmit": true` to
   `tsconfig.json` and change the `build` script to `tsc --noEmit && vite build` so this
   cannot regenerate.
3. Rewrite `STACK.md` to describe the actual mp3-manager stack and architecture.
4. Create `THESAURUS.md` with mp3-manager's real domain terms (Root/Workspace, Track,
   TrackMetadata, VfsAdapter, checksum, grouping mode flat/wizard, MetaSnapshot, etc.).
5. Adopt a minimal slice of rom-manager's architecture, scoped conservatively to avoid
   over-engineering:
   - New `src/services/ThemeService.ts`: dark/light theme persisted + system-preference
     fallback, following rom-manager's `initTheme()` pattern.
   - New small `src/components/ThemeToggle.tsx` (presentational, no store coupling, per
     user preference) wired from `App.tsx`.
   - Add `[data-theme="dark"]` CSS variable overrides in `styles.css` (no full redesign).
   - Full i18n extraction and a `core/` split of existing `lib/`/`vfs/` logic are
     **out of scope for this session** (large, invasive, no translation content
     requested) — left as backlog items below.

## Backlog (not done in this session)

- Full i18n layer (extract all hardcoded Spanish strings into an `I18nService`).
- Splitting `lib/`/`vfs/` into `core/`/`services/` folders to mirror rom-manager exactly.
- Landing/welcome screen before the folder picker.

## Extension (2026-08-01 16h20): metadata loading performance + follow-up UX issues

User reported, after using the app:
1. Folder/tree navigation "works quite badly" (no repro details given yet).
2. On refresh, you have to wait for metadata to load sequentially; file access and
   metadata parsing should be combined/overlapped to speed things up.
3. The wizard-mode marker is "in the folder", not in the header.
4. There is no "consolidate" button.
5. The detail view (`MetadataEditor`) still doesn't look like rom-manager's game detail
   view (`RomDetails.tsx`) at all.

### Done in this extension

- **Performance (item 2)**: `hydrateRoot` in `Mp3ManagerView.tsx` used to read bytes,
  hash, and parse ID3 tags for one track at a time in a strictly sequential `for`
  loop. Replaced with a bounded worker pool (`READ_CONCURRENCY = 6`): several tracks'
  file reads/hashing/parsing now run concurrently, overlapping disk I/O with CPU-bound
  parsing, while keeping the same batched UI flush (every 10 completed tracks) and the
  same metadata-cache-by-checksum behavior. Verified with `npm run build`.

### Needs clarification before implementing (see chat)

- Item 1 (navigation bug): no concrete repro yet — investigated keyboard nav
  (`handleLibraryKeyDown`) and root-tab switching (`handleSelectRoot` /
  `resyncRootIfNeeded`); nothing conclusively broken was found without a repro. Notably,
  arrow-key navigation is wizard-mode-only today (flat mode has none).
- Item 3 (wizard marker location): the Flat/Wizard switch already lives in the header
  (`header-right-actions`) in the current code, not per-tab/per-folder — asked user what
  element they mean.
- Item 4 (consolidate button): mp3-manager has no rename/move ("organize") feature at
  all yet, unlike rom-manager's plan-first `OrganizePanel`/`rom-organize.ts`. This
  renames/moves real user files, so scope (naming scheme, undo) needs to be defined
  before writing it — asked user for the intended behavior.
- Item 5 (detail view redesign): rom-manager's `RomDetails.tsx` is a large, multi-section
  view (cover hero, facts grid, checksum row, editing mode). Asked user which specific
  elements they want mirrored for `MetadataEditor` rather than guessing a full redesign.

### User answers (clarifying round)

1. Navigation: "opening a new folder doesn't refresh the tree well." Root cause found:
   in wizard mode, all tracks start bucketed under a single "Sin album" group (metadata
   not loaded yet) and reshuffle into their real albums as batches complete — a
   confusing, constantly-restructuring tree during load.
2. Wizard marker: pointed to rom-manager's `.tree-organize` inline button pattern
   (split tree-item layout: left toggle/label, right action button) as the reference.
3. Consolidate button: for now a **placeholder only** — the actual mp3tag-style naming
   pattern will be designed in a future session.
4. Detail view: wants (a) a big cover on top instead of the small dropzone, (b) a facts
   grid with file name, size, path and checksum, (c) an explicit Edit/Save mode (already
   existed), plus (d) a play button for the audio file.

### Done in this extension (continued)

- **Wizard tree loading state (item 1)**: while `activeRoot.loadingMetadata` is true,
  the library pane now shows a stable "Cargando metadatos..." placeholder instead of
  the reshuffling album/disc tree; the real `TrackWizardList` only renders once loading
  finishes. Flat mode (`TrackTable`) is unaffected (it already handled loading gracefully
  since it doesn't regroup rows).
- **Consolidate placeholder (items 2+3)**: `TrackWizardList` track rows are now a split
  layout (`.tree-item`: left selectable row + right `.tree-organize` button, mirroring
  rom-manager's pattern). Clicking it calls `handleConsolidateTrack`, which currently just
  shows an info message that the naming pattern is still to be defined.
- **Detail view redesign (item 4)**: `MetadataEditor` now renders a `.metadata-hero` with
  a big cover on the left (`.cover-hero`, reusing the existing cover image/dropzone/empty
  styles) and title/tags/audio-player on the right, in both view and edit mode. The facts
  grid gained "Ruta" and "Checksum" entries. Added a new small reusable
  `TrackAudioPlayer` component (`src/components/TrackAudioPlayer.tsx`): a "Reproducir"
  button that lazily reads the track's bytes through the VFS, builds a Blob object URL,
  and swaps in a native `<audio controls>` element; the object URL is revoked on track
  change/unmount.
- Verified with `npm run build` after each step (type-check + `vite build` succeed).
