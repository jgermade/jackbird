## 2026-11-12 18:15 UTC — The service's one-line setup: `setup.sh`

The owner's order of 2026-11-12: "for the binary we should have a one-line setup,
https://jgermade.github.io/jackbird/setup.sh, that offers the user the options: install,
re-install, update, uninstall".

- **`landing/setup.sh`** (POSIX sh; `scripts/build-landing.mjs` copies `landing/` whole, so it is
  published at the site's root). `curl -fsSL https://jgermade.github.io/jackbird/setup.sh | sh`:
  - It tells the machine (Linux x64 or arm64, macOS arm64 or x64; a shell under Rosetta counts as
    arm64; Windows and anything else are told where to go), how the service is installed, if it
    is (its registration is there, as `installed()` in `crates/service/src/install.rs` tells it:
    at logon first, then with the system), its version, whether it answers (`status`), and the
    latest release (where the releases' "latest" page leads).
  - It asks on the terminal (`/dev/tty`: the script itself comes down the pipe): not installed,
    **Install**; installed, **Update**, **Re-install** or **Uninstall**. Installing, it asks how
    the service starts (with the system, the default, or at logon) and afterwards offers the
    service's own `setup` (sign-in, the first owner).
  - It does nothing itself but fetch the release's binary for the machine
    (`releases/latest/download/…`, or `--version vX.Y.Z`; curl or wget; a temporary folder, the
    home's `.cache` where `/tmp` runs nothing) and run that binary's `install`, `update` or
    `uninstall`, with `sudo` (and `--user`, `--uid`, `--home`) where the service is with the
    system. Re-installing fetches first, so a failed download leaves the service as it is, then
    uninstalls and installs the way it was (or the way given). Updating to the version installed
    says so and does nothing. Uninstalling asks first and uses the installed binary. The library
    and the configuration are the binary's to keep: it never removes them.
  - With no questions: `sh -s -- install [--logon] | reinstall | update | uninstall [--yes] |
    status`; with no command and no terminal, the usage. Run with sudo, it refuses (it would
    install for root): it asks for administrator rights itself.
  - It does not put `jackbird-service` on the PATH (the binary's own installation does not): it
    prints the installed binary's path for `setup`.
- **`scripts/setup-check.mjs`**, in `npm test` (`test:setup`): the script run against a stand-in
  binary under a temporary home and root (`JACKBIRD_SETUP_BINARY`, `JACKBIRD_SETUP_ROOT`, there
  for this): ten checks, of each command, both ways, what is refused and what is asked.
- **`landing/index.html`**: the binary's card leads with the one line, says what it does, links
  the script to read, and keeps the binaries' links. **`docs/install.md`**: the same, with the
  commands without questions.

Checked here: `shellcheck -s sh` and `dash -n` clean; the check's ten cases; the menu on a
pseudo-terminal (install at logon, then uninstall); and for real against v0.1.18, which it
downloaded and ran: the binary answered that this machine runs no systemd, and the script said it
could not be installed and left nothing behind. **Not checked**: a real installation (no systemd
here), and macOS. It goes live with the next release's site.
