# Deck: a design system of our own

**Date**: 2026-11-03 18:35
**Summary**: Study luu's default theme and propose MP3 Manager's own design system, "Deck", whose
style evokes old portable audio gear (Walkman, Discman, iPod, hi-fi decks).

## 1. What luu's default theme does

`web/theme/default/` in luu (see its `RECORD/2026-10-21.a-design-system-of-components.completed.md`):

- **A theme is a folder**: `tokens.css` (every value), `components/` (one file each), and a demo
  page that shows them all. A second theme replaces the folder.
- **Tokens by role, not by hue**: grounds (`bg`, `sunken`, `surface`, `field`), inks (`fg`,
  `fg-muted`, `fg-subtle`), four tones (`accent`, `ok`, `warn`, `bad`), each with a `-soft`
  ground. Plus type, space, radii, control heights, shadows and motion.
- **Light on `:root`, dark on `[data-theme="dark"]`**, and any element can be an island of the
  other tone with `data-tone`.
- **Components read tokens with no fallback**: a missing token should look missing, not quietly
  draw a copy of the palette.
- **`prefers-reduced-motion` zeroes the durations once**, in `tokens.css`.
- **App-only tokens live apart** (`luu.css`) from what components need (`tokens.css`).
- **Built beside the app first**; screens move over one at a time.

What we take: the structure and all of the rules above.
What we don't take: the values (palette, type, shape), the jq79 component format (this project is
React), and luu's own surfaces (chat, terminal, context buckets).

## 2. Where mp3-manager stands

- `src/styles.css`: 1718 lines, ~129 top-level classes, 12 colour variables (`--bg`, `--chrome`,
  `--panel`, `--accent`, …) and 56 hard-coded colours outside them. Radii, spacing and type sizes are literals.
- The fonts it names (IBM Plex Sans/Mono, Space Grotesk) are **never loaded**: `index.html` has no
  font link and there is no `@font-face`, so every user gets a system fallback.
- `ThemeService.ts` sets `data-theme` on `<html>`; that stays the switch.
- `index.html` says `lang="es"` and several UI strings are Spanish; both conflict with the
  English-only rule in `AGENTS.md` (see §8).

## 3. Direction

Five rules, which the preview shows:

1. **Evoke, don't copy.** No real product's look: no click wheel, no logos, no chrome photos.
   The references are materials and habits, not a device.
2. **One signal colour.** Signal orange means "this one": the primary key, the selection, a lit
   LED, the playing track. Nothing decorative is orange.
3. **Displays show state.** Now playing, counters and scan progress go in a display window: a
   reflective LCD in the light tone, a VFD in the dark one.
4. **Keys travel.** A pressed key moves 1px down with an inset shadow. Keys sit in banks (a
   recessed well); a latched key stays down with its LED lit.
5. **Printed labels.** Section heads, column heads and field labels are small, wide, uppercase
   and letter-spaced, like the print on a faceplate.

Everything outside those signature elements stays flat and quiet: no textures beyond a faint
brushed line on the faceplate, no skeuomorphic photos.

## 8. Cost, rejected options, open questions

**Cost**: four font dependencies (~100–200 KB of woff2, latin subsets only), one extra Vite entry,
and a gradual rewrite of `styles.css` (steps 2–5).

**Rejected**:

- *Skeuomorphic realism* (photo textures, brushed-metal images, 3D knobs): heavy, ages badly and
  costs legibility. Five signature elements carry the style instead.
- *Re-skinning luu's `tokens.css`*: the user asked for a style of our own. We keep its structure
  and none of its values.
- *Porting luu's components*: they are jq79; this app is React.
- *Replicating a specific device* (click wheel, a Walkman's faceplate): it would be a copy, not a
  style.
- *Google Fonts at runtime*: no dependency, but it needs the network and calls a third party from
  a local-first app.

**Open questions for the user**:

1. Name: `deck` (`src/theme/deck/`), or `default` as in luu?
2. Fonts: self-host with Fontsource (four dependencies) or link Google Fonts?
3. Light chassis: silver as proposed, or a dark chassis in both tones, as luu does with its bars?
4. The English-only rule: translate the Spanish UI strings and `lang="es"` as part of this work,
   or in a separate record?
5. Once approved, write the plan in §7 as a Gantt chart under `ROADMAP/2026-11-03/`?

## Extension — 2026-11-03 18:54 — Proposal: the UI on jq79, in four layers

**Status**: proposal, awaiting approval. Nothing changed for it yet.

User (translated): *"For the UI, how about we use jq79, where:*
- *`components/`: components that depend on no store, only on themselves or on helpers;*
- *`helpers/`: TypeScript functions that depend only on other helpers, ideally with no
  dependencies, and ideally with as much test coverage as possible;*
- *`lib/`: factories, services, stores, etc.; they can depend on helpers and on other `lib/`
  functions;*
- *`views/`: jq79 components that bring the data and the components together."*

### What jq79 is

- npm `jq79` 0.7.7 (luu vendors 0.7.6), ISC, by this project's author. One file, no dependencies.
- A component is an `.html` file: a `<script :setup>` (Svelte-style: `$:` declarations,
  `$emit`, `await $mounted()`, `$destroyed`), a template (`{{ }}`, `:attr`, `:if`, `:each` with
  `:key`, `@event`, slots) and `<style scoped>`. `$reactive` stores with `$on`, `$effect` and
  `$computed`. Proxy-based, fine-grained updates with no virtual DOM.
- It loads two ways. At runtime, with `C79.fetch("./x.html")`: no build, which is what luu does
  because its UI ships inside a Rust binary. Or through its Vite plugin, `jq79/vite`: `.html`
  files import as modules, the imports in a setup script are hoisted so Vite bundles them,
  `<script :setup lang="ts">` has its types stripped, styles go through Vite's CSS pipeline,
  and edits hot-reload. The plugin can also precompile setup scripts (`safeEval`) so the page
  runs without `'unsafe-eval'`.

### Proposal

**Keep Vite, add `jq79/vite`, and replace React.** The four layers ask for TypeScript, which
needs a compile step anyway; Vite already is one, and with the plugin a setup script can
import a `.ts` helper and have it bundled.

```
src/
  helpers/      pure TypeScript; imports only other helpers; no DOM, no stores, no packages
  lib/          stores ($reactive), services, factories: library, playback, selection,
                preferences (theme, language), i18n, VFS, id3, session persistence
  components/   jq79 .html; no store; imports helpers and other components only
  views/        jq79 .html; reads lib/, composes components/
  locales/      en.ts (source and fallback), es.ts
  main.ts       mounts the root view
theme/default/
  tokens.css, fonts.css, fonts/   unchanged
  components/*.html               the Deck components, ported to jq79 (the design system;
                                  src/components/ holds the app's own pieces built from them)
  index.html, demo.html           the demo, as a jq79 page
```

| Layer | May import |
| --- | --- |
| `helpers/` | `helpers/` |
| `lib/` | `helpers/`, `lib/`, `jq79` (for `$reactive`), packages |
| `components/` (app and theme) | `helpers/`, `components/` |
| `views/` | all of the above |

`src/types.ts` (types only, erased at build) stays importable from every layer.

- **The rule is checked, not just written**: a dependency-free script (`scripts/check-layers.mjs`)
  reads the imports of every file under `src/` and `theme/` and fails on an import the table
  forbids. It runs with the tests.
- **Helpers are tested with Node's own runner**, so tests add no dependency:
  `node --test --experimental-strip-types --experimental-test-coverage`, with coverage
  thresholds on `helpers/` (`--test-coverage-lines`, `-branches`, `-functions`). Node runs
  `.ts` directly, so helpers use only erasable syntax (no `enum`, no `namespace`) and import
  each other with the `.ts` extension (`allowImportingTsExtensions`, valid with `noEmit`).
  Tests live beside the helper (`format.ts`, `format.test.ts`).
- **Where today's code goes**: the pure functions at the bottom of `Mp3ManagerView.tsx`
  (`computeCommonMetadata`, `getVariedFields`, `inferDiscLabel`, `trackNumberOrder`,
  `orderDetailPlaylist`, `collectFolderPaths`, `buildWizardRows`) move to `helpers/` with tests;
  its 15 pieces of React state become `lib/` stores; `ThemeService`, `rootSessionStore` and
  `id3` move to `lib/` (`id3` wraps two packages, so it is not a helper; the byte-level parts
  that need no package can become helpers).
- **i18n fits the layers**: lookup with English fallback and `{param}` filling is a helper;
  the chosen language (browser default, saved in Preferences) is a `lib/` store; the texts
  are `locales/en.ts` and `locales/es.ts`.

### Migration: gradual, one screen at a time

React and jq79 can share a page: a jq79 view mounts into an element React renders. So:

1. **Theme in jq79**: port the Deck components and the demo to `.html`; tokens, fonts and almost
   all of the CSS carry over into each `<style scoped>`. The React versions from phase 1 are
   deleted once the port is in.
2. **Layers and tests**: `helpers/` with the functions above and their tests, the coverage
   thresholds and the layer check.
3. **Stores and i18n**: move the view's state into `lib/` stores. React reads them through a
   small hook for as long as it is still there, so the app keeps working between steps.
4. **Views on jq79**, replacing React screens in roadmap order: faceplate, library, modals and
   forms.
5. **Remove React** and clean up `styles.css`.

### Cost and risks

- **Templates are not type-checked.** `lang="ts"` setup scripts lose their types, they are not
  checked. Setup scripts therefore stay thin, and the logic lives in typed, tested
  helpers and `lib/`.
- **jq79 is pre-1.0.** luu has found and upstreamed gaps (a teardown hook, effect batching). Our
  heaviest workload is the library tree: up to a few thousand rows with selection. `:each` with
  `:key` keeps rows that did not change; virtualising the tree, if needed, is ordinary component
  code.
- **Two frameworks for a while**: the bundle is larger until step 5.
- **Phase 1's React components are discarded** after step 1 (~1 000 lines of TSX); the tokens,
  the fonts, the CSS and the demo's content stay.
- `RECORD/2026-08-11.musikmatch-rust-migration.WIP.md` says the desktop build "reuses the React
  UI"; with this it reuses the jq79 one. Tauri serves any static build, so nothing else there
  changes.

### Rejected

- **jq79 without Vite (runtime fetch, as luu does)**: the TypeScript helpers and `lib/` would
  need a compile step of their own, and the bundling and hashed assets would go. luu needs it so

## Extension — 2026-11-04 01:32 — Fixing the verifier: plan

User: *"fix the verifier bug"*, the known issue at the end of the 00:19 extension.

### What goes wrong, exactly

Two paths end with the same bad `.meta` record: a track's **new** checksum paired with its
**old** tags. The record's size and date no longer match the file, so the next load re-reads
the file. The checksum then matches the record, so the load takes the record's tags, which
are the old ones.

1. **A save during a run.** The verifier works from the snapshot object and the track objects
   it captured when the run started. A save replaces the root's snapshot. The verifier's next
   step puts its own snapshot back (in place, mutating it) and later writes it to `.meta`,
   which undoes the save's entries. If an edited track is still on the run's list, the
   verifier reads its new bytes but records them with the tags captured at the start.
   Meanwhile, the save had copied the snapshot when it started, so verifications made during
   the save are lost from `.meta` as well. That second loss is harmless; they are re-verified
   later.
2. **A file changed outside the app.** When the checksum the verifier computes differs from
   the library's, it records it as verified, still with the library's tags.

### The fix

- `helpers/snapshot.ts`, tested:
  - `checksumOf(track)`;
  - `applyVerification(root, trackId, readFrom, found, nowIso)`, which gives the root after
    one verification, without mutating anything. The track and its record take the checksums
    and the time, and keep the track's **current** tags, size and date. If `found.file` says
    the file changed (its tags, size and date as read now), they take those instead.

    It gives `null` when the result no longer applies: the track is gone, or its checksum is
    no longer `readFrom`, the one it had when its file was read (a save or a rescan recorded
    the file since).
- `lib/meta.ts`: `flushMeta(rootId)` writes the root's snapshot **as it is when the write
  starts**. Writes for a root are queued, so two never overlap and the last one written is

The owner's ask of 2026-11-12, planned in `ROADMAP/2026-11-13/desktop-compact-mode.md`; on

built:

- **One display, two places (C1).** The faceplate's display (the mark at the left that turns
  between format, spectrum and DAC; the title and the artist; the clock; the meter) moves out of

- **The window (C2)**, through `@tauri-apps/api/window` (already a dependency): before turning

### Opening a folder, fast

The owner: opening folders is slow in the macOS app; "the logic should be in memory"; "could it
be needless rerenders?". Measured here in the desktop app on Linux (WebKitGTK, software rendering,
`target/bench`, a check folder ending in `#bench` timed by a throwaway patch of `check.ts`), on a
library of 240 MP3s over 20 albums (covers of 45 to 300 KB) and on five copies of it (1,200):

| | before | covers once | now |
| --- | --- | --- | --- |
| 240, first opening, tags shown | 172 s | 175 s | 1.1 s (checksums at 2.2 s) |
| 240, reopened | 7.9 s | 7.3 s | 2.2 s |
| `.meta/mp3-manager.json` | 29.4 MB | 174 KB | 174 KB |
| 1,200, first opening | did not finish in 400 s | | 4.3 s (checksums at 6.3 s) |

(Reopened, the session also reopens the folder: it is opened twice, in every column.)

1. **Each cover kept once.** Every track carried its album's picture as a data URL: twelve copies
   per album in memory, in every update of the library, in the page, over the IPC, and in `.meta/`,
   read whole at each opening. The library holds references now, `jackbird-cover:<name>`, the name
   made from the bytes (two FNV-1a hashes and the length, and the type's extension: `coverName` in
   helpers/cover.ts, `cover_name` in crates/api, the same test vectors). `lib/covers.ts` keeps each
   picture once, as bytes, draws it through a blob URL made when first shown (`coverSrc`), reads
   one only named from the folder's `.meta/covers/<name>`, and writes it there before the snapshot
   that names it (one that cannot be written stays in the snapshot whole). A source's results come
   with references (`withCovers`); a cover given by reference is written whole when it is not the
   track's own (crates/api's `edit_for` keeps a cover only when it is the same string). An older
   `.meta/` is taken by reference and written again so; a track whose picture is missing from
   `.meta/covers/` has its tags read again. The phone's lock screen takes a data URL, made from the
   bytes in memory (`coverDataUrlNow`).
2. **Tags first, checksums after.** `crates/core` has `inspect`'s two halves: `read_tags` (the head
   only) and `checksums` (the whole file, streamed). The library shows with the tags; the verifier
   works the missing checksums out in bulk at once (`applySums`, one pass), and leaves a file that
   changed since its tags were read to its one-at-a-time pass, which reads its tags again: a new
   checksum is never recorded with old tags.
3. **In bulk, in Rust.** `src-tauri/src/scan.rs`: `scan`, every file's tags at once on a few threads
   (2 to 8), sent in batches over a channel (every 150 ms or 256 files); each cover met for the
   first time written into `.meta/covers/` by Rust (sent in the batch only when it cannot be
   written), so no picture crosses the IPC; `checksums`, the same way, on up to 4 threads. The last
   batch says `done`: the interface waits for it, not for the command's answer, which can come
   first. `hydrateRoot` uses it where the source has it (`scanTags`): one call for the folder, a new
   file coming in with its tags (no empty row drawn first), the count from the walk (`total`).
4. **The rerenders.** Profiled in Chromium: a quarter of the time was `Intl.PluralRules` made anew
   for each plural, by the menus; every update of the library built every row's menu, and drew its
   items, closed. `Menu` takes its items as a function, made and drawn only when it opens; the rules
   are made once per language. The browser's tag engine keeps a cover from its bytes, never through
   a data URL. The update after the tags went from 1.3 s to 0.9 s here, the one after the
   checksums from 1.1 s to 0.1 s; what is left is one drawing of the library, slow in this
   software-rendered WebKit.

Also: two lookups that were linear per file (removed tracks, a track's checksum now) go through a
set and a map. The desktop check (`JACKBIRD_CHECK_FOLDER`) saves a title into a file of its folder:
pointed at `fixtures/tags` it changes a fixture (it did here once, restored).

Not done: `.meta/covers/` keeps a picture no track names any more; the songs view's other views
still draw every album's tracks in Details at once.
