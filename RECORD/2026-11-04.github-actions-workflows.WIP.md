# GitHub Actions: build, release and deploy

**Date**: 2026-11-04 04:55
**Summary**: Three GitHub Actions workflows: `build.yml` runs the tests and bundles with Vite,
`release.yml` bumps the version, builds, publishes a GitHub release with the build attached and
optionally deploys it, and `deploy.yml` deploys any released tag (`latest` by default).

**Status**: Proposal, awaiting approval. Nothing under `.github/` exists yet.

User request (translated): *"Add GitHub Actions workflows:*

- *`build.yml`: runs the tests and makes the bundle with Vite.*
- *`release.yml`: bumps the version (input: major, minor, patch), runs `build.yml`, creates a
  release, attaches the build to it, and deploys it (runs `deploy.yml`) on GitHub Actions if the
  user ticked the checkbox in the run (input: `deploy`).*
- *`deploy.yml`: deploys the given tag (input: `tag`), with `latest` as the default value."*

---

## 1. Where the project stands

- No `.github/` folder: no workflows, no Dependabot.
- `npm test` runs the layer check, the helpers' type check, the unit tests (Node's own runner with
  `--experimental-strip-types`, so Node 22.6 or later) and the 90% coverage floor. It passes.
- `npm run build` is `tsc --noEmit && vite build`, with two entries: the app (`index.html`) and
  the theme demo (`theme/default/index.html`). Output goes to `dist/` (ignored by git).
- `vite.config.ts` sets no `base`, so the build expects to be served from `/`. GitHub Pages
  serves this repository from `https://jgermade.github.io/jackbird/`, under `/jackbird/`, so a
  root-based build would load nothing there.
- `package.json` is at `0.1.0`; the repository has no tags and no releases.
- The app never reads its own version, and has no client-side routing (one page, no
  `history.pushState`).

## 2. Decisions proposed

1. **Deploy target: GitHub Pages, deployed from Actions** (`actions/configure-pages`,
   `actions/upload-pages-artifact`, `actions/deploy-pages`). The app is static and has no backend,
   which is what Pages serves.
2. **Build once, deploy that build.** `deploy.yml` does not rebuild: it downloads the zip attached
   to the release and publishes it. What is deployed is exactly what was tested and released.
3. **Relative base (`base: "./"` in `vite.config.ts`).** So that one build works under any path
   (`/jackbird/` on Pages, `/` locally or on another host). Checked: with `--base=./`, the build
   writes `./assets/…` in `index.html` and `../../assets/…` in the theme demo, and nothing in the
   code builds an absolute URL. The dev server is unaffected (Vite serves a relative base from `/`).
4. **Versions follow `npm version`.** `npm version <major|minor|patch>` bumps `package.json` and
   `package-lock.json`, commits (`chore(release): x.y.z`) and tags `vx.y.z`. The commit and the
   tag are pushed together (`git push --atomic`) to the branch the release runs on, which must be
   the default branch.
5. **Node 22** on the runners, the version the project already uses locally and the first LTS
   that runs the tests (`--experimental-strip-types`).

## 3. The three workflows

### `.github/workflows/build.yml`

- **Runs on**: push to `main`, every pull request, by hand (`workflow_dispatch`) and when called
  by another workflow (`workflow_call`, with an optional `ref` input: what to check out).
- **Steps**: checkout → set up Node 22 with the npm cache → `npm ci` → `npm test` →
  `npm run build` → upload `dist/` as the `dist` artifact.
- **Permissions**: `contents: read`.

### `.github/workflows/release.yml`

- **Runs on**: by hand only, with two inputs:
  - `bump`: a choice of `major`, `minor`, `patch` (default `patch`).
  - `deploy`: a checkbox, unticked by default.
- **Jobs**, in order:
  1. `version`: refuses to run off the default branch; `npm version <bump>` as
     `github-actions[bot]`; pushes the commit and the tag atomically; outputs the tag (`vx.y.z`).
  2. `build`: calls `build.yml` with `ref` set to the new tag, so the tests and the bundle run on
     the released commit.
  3. `release`: downloads the `dist` artifact, zips it as `jackbird-vx.y.z.zip`, and creates the
     GitHub release for the tag with that zip attached and notes generated by GitHub
     (`gh release create --generate-notes --verify-tag`).
  4. `deploy`: only if `deploy` was ticked; calls `deploy.yml` with the new tag.
- **Permissions**: `contents: write` for the version and release jobs; the deploy job grants the
  ones Pages needs (`pages: write`, `id-token: write`).
- **Concurrency**: one release at a time (`group: release`, never cancelled).

### `.github/workflows/deploy.yml`

- **Runs on**: by hand (`workflow_dispatch`) and when called (`workflow_call`), both with a `tag`
  input whose default is `latest`.
- **Steps**: resolve `latest` to the latest release's tag → download that release's
  `jackbird-*.zip` → unzip → `actions/configure-pages` → `actions/upload-pages-artifact` →
  `actions/deploy-pages`, in the `github-pages` environment, which shows the page URL in the run.
- **Permissions**: `contents: read`, `pages: write`, `id-token: write`.
- **Concurrency**: one deployment at a time (`group: pages`, never cancelled), as GitHub
  recommends for Pages.

## 4. What the repository needs once (by hand, in GitHub's settings)

- **Settings → Pages → Source: GitHub Actions.** `deploy.yml` fails until this is set; the
  workflow token cannot turn Pages on by itself.
- **The default branch must accept pushes from `github-actions[bot]`.** If `main` gets a branch
  protection rule or ruleset that requires pull requests, the release's version push fails, and
  the bot must be allowed to bypass it.

## 5. Known limits

- Pushes and releases made with the workflow token start no other workflow. That is why
  `release.yml` calls `build.yml` and `deploy.yml` directly, and why the version commit does not
  trigger a second build on `main`.
- If the build fails after the version was pushed, the tag stays without a release. Fixing the
  cause and running the release again makes the next version; the empty tag can be deleted by
  hand.
