# GitHub Actions: build, release and deploy

**Date**: 2026-11-04 04:55
**Summary**: Three GitHub Actions workflows: `build.yml` runs the tests and bundles with Vite,
`release.yml` bumps the version, builds, publishes a GitHub release with the build attached and
optionally deploys it, and `deploy.yml` deploys any released tag (`latest` by default).

**Status**: Proposal, awaiting approval. Nothing under `.github/` exists yet.

User request (translated): *"Add GitHub Actions workflows:*

- *`build.yml`: runs the tests and makes the bundle with Vite.*
- *`release.yml`: bumps the version (input: major, minor, patch), runs `build.yml`, creates a
  release, attaches the build to it, and deploys it (runs `deploy.yml`) on GitHub Actions if the
  user ticked the checkbox in the run (input: `deploy`).*
- *`deploy.yml`: deploys the given tag (input: `tag`), with `latest` as the default value."*

## 1. Where the project stands

- No `.github/` folder: no workflows, no Dependabot.
- `npm test` runs the layer check, the helpers' type check, the unit tests (Node's own runner with
  `--experimental-strip-types`, so Node 22.6 or later) and the 90% coverage floor. It passes.
- `npm run build` is `tsc --noEmit && vite build`, with two entries: the app (`index.html`) and
  the theme demo (`theme/default/index.html`). Output goes to `dist/` (ignored by git).
- `vite.config.ts` sets no `base`, so the build expects to be served from `/`. GitHub Pages
  serves this repository from `https://jgermade.github.io/jackbird/`, under `/jackbird/`, so a
  root-based build would load nothing there.
- `package.json` is at `0.1.0`; the repository has no tags and no releases.
- The app never reads its own version, and has no client-side routing (one page, no
  `history.pushState`).

## 2. Decisions proposed

1. **Deploy target: GitHub Pages, deployed from Actions** (`actions/configure-pages`,
   `actions/upload-pages-artifact`, `actions/deploy-pages`). The app is static and has no backend,
   which is what Pages serves.
2. **Build once, deploy that build.** `deploy.yml` does not rebuild: it downloads the zip attached
   to the release and publishes it. What is deployed is exactly what was tested and released.
3. **Relative base (`base: "./"` in `vite.config.ts`).** So that one build works under any path
   (`/jackbird/` on Pages, `/` locally or on another host). Checked: with `--base=./`, the build
   writes `./assets/…` in `index.html` and `../../assets/…` in the theme demo, and nothing in the
   code builds an absolute URL. The dev server is unaffected (Vite serves a relative base from `/`).
4. **Versions follow `npm version`.** `npm version <major|minor|patch>` bumps `package.json` and
   `package-lock.json`, commits (`chore(release): x.y.z`) and tags `vx.y.z`. The commit and the
   tag are pushed together (`git push --atomic`) to the branch the release runs on, which must be
   the default branch.
5. **Node 22** on the runners, the version the project already uses locally and the first LTS
   that runs the tests (`--experimental-strip-types`).

## 3. The three workflows

### `.github/workflows/build.yml`

- **Runs on**: push to `main`, every pull request, by hand (`workflow_dispatch`) and when called
  by another workflow (`workflow_call`, with an optional `ref` input: what to check out).
- **Steps**: checkout → set up Node 22 with the npm cache → `npm ci` → `npm test` →
  `npm run build` → upload `dist/` as the `dist` artifact.
- **Permissions**: `contents: read`.

### `.github/workflows/release.yml`

- **Runs on**: by hand only, with two inputs:
  - `bump`: a choice of `major`, `minor`, `patch` (default `patch`).
  - `deploy`: a checkbox, unticked by default.
- **Jobs**, in order:
  1. `version`: refuses to run off the default branch; `npm version <bump>` as
     `github-actions[bot]`; pushes the commit and the tag atomically; outputs the tag (`vx.y.z`).
  2. `build`: calls `build.yml` with `ref` set to the new tag, so the tests and the bundle run on
     the released commit.
  3. `release`: downloads the `dist` artifact, zips it as `jackbird-vx.y.z.zip`, and creates the
     GitHub release for the tag with that zip attached and notes generated by GitHub
     (`gh release create --generate-notes --verify-tag`).
  4. `deploy`: only if `deploy` was ticked; calls `deploy.yml` with the new tag.
- **Permissions**: `contents: write` for the version and release jobs; the deploy job grants the
  ones Pages needs (`pages: write`, `id-token: write`).
- **Concurrency**: one release at a time (`group: release`, never cancelled).

### `.github/workflows/deploy.yml`

- **Runs on**: by hand (`workflow_dispatch`) and when called (`workflow_call`), both with a `tag`
  input whose default is `latest`.
- **Steps**: resolve `latest` to the latest release's tag → download that release's
  `jackbird-*.zip` → unzip → `actions/configure-pages` → `actions/upload-pages-artifact` →
  `actions/deploy-pages`, in the `github-pages` environment, which shows the page URL in the run.
- **Permissions**: `contents: read`, `pages: write`, `id-token: write`.
- **Concurrency**: one deployment at a time (`group: pages`, never cancelled), as GitHub
  recommends for Pages.

## 4. What the repository needs once (by hand, in GitHub's settings)

- **Settings → Pages → Source: GitHub Actions.** `deploy.yml` fails until this is set; the
  workflow token cannot turn Pages on by itself.
- **The default branch must accept pushes from `github-actions[bot]`.** If `main` gets a branch
  protection rule or ruleset that requires pull requests, the release's version push fails, and
  the bot must be allowed to bypass it.

## 5. Known limits

- Pushes and releases made with the workflow token start no other workflow. That is why
  `release.yml` calls `build.yml` and `deploy.yml` directly, and why the version commit does not
  trigger a second build on `main`.
- If the build fails after the version was pushed, the tag stays without a release. Fixing the
  cause and running the release again makes the next version; the empty tag can be deleted by
  hand.

## Extension — 2026-11-04 12:20 — WebAssembly for tags? Measurements; the FLAC risk; a data loss found in MP3 saves: findings and proposals

**Summary**: Two questions, answered with measurements. WebAssembly would not speed up what is
slow; what is slow is identified, with proposals. The FLAC risk is spelled out. On the way: saving
an MP3 today drops every ID3 frame jackbird does not edit. Nothing is changed yet: the proposals
below await approval.

User questions (translated): *"Would using WebAssembly for reading/writing tags improve
performance?"* and *"Explain the risk of FLAC tags better."*

### Where the time goes (measured)

Chromium in this container, medians of 7–9 runs, a 13 MB MP3 (5 min at 320 kbps) with a 1.27 MB
JPEG cover, through `src/lib/id3.ts` as the app runs it (`.tmp/scripts/bench-tags.cjs`,
`bench-hash.cjs`, `bench-cover.cjs`; a first, cold run gave higher numbers and is left out):

| Step | ms |
| --- | --- |
| Read the file (OPFS) | 15–18 |
| SHA-1 of the whole file (WebCrypto, with the copy `sha1Hex` makes) | 30 |
| SHA-1 of the audio only (the same) | 30 |
| Read the tags (`jsmediatags`, then the cover to a data URL) | 149 |
| — of which the cover to a data URL, one character at a time | 46–66 |
| Write the tags (`browser-id3-writer`, with the cover) | 93 |
| Write the file back | 61 |

The same 13 MB hashed other ways: WebCrypto SHA-1 without the copy 15 ms; SHA-1 in WebAssembly
(`hash-wasm` 4.12.0, installed in `.tmp/bench` only) 51 ms; BLAKE3 in WebAssembly 37 ms. The 1.27 MB
cover to a URL: one character at a time 52 ms; `FileReader.readAsDataURL` 7 ms; an object URL 2 ms.

**So**: the hashing is already native and faster than WebAssembly. Reading tags is slow because of
how it is done (`jsmediatags` gets a copy of the whole file as a `File` and hands the cover back as
an array of numbers; `id3.ts` builds the data URL one character at a time), not because it is
JavaScript; a WebAssembly parser would also need the file copied into its memory. All of it runs on
the main thread, which a WebAssembly module does not change by itself.

And one cost not in the table: each track's cover is kept in `.meta/mp3-manager.json` as a data URL
(1.66 MB of text for this cover), once per track, so an album of 12 such tracks puts some 20 MB in
the file, which is serialised and written whole on every save and every verifier flush. (Estimate:
1,000 tracks with 200 KB covers, some 270 MB.)

### Proposals (awaiting approval), by gain

1. **Covers out of `.meta` and out of data URLs**: each distinct cover stored once (by its hash,
   e.g. `.meta/covers/<sha1>.jpg`), records keep only the hash, the views show it through an
   object URL. The largest gain for real libraries; needs a migration of existing `.meta` files.
2. **A lean ID3v2 reader** in `src/helpers/` (pure, tested): read the tag's size from its header,
   parse only those bytes, return the cover as bytes. Replaces `jsmediatags` for MP3.
3. **Scanning in a Web Worker**: reading, hashing and parsing off the main thread, so the interface
   stays smooth during a first scan.
4. **One hash instead of two** (~30 ms a file): hash the tag and the audio separately and derive
   the full checksum from both; also a `.meta` migration.

WebAssembly would make sense for another reason: a mature tagging library compiled to it (TagLib
has such ports) could read and write MP3, FLAC, Ogg and M4A with one well-tried writer. That is
about correctness and formats, not speed, and costs a large binary to download.

### Found: saving an MP3 drops the frames jackbird does not edit

`browser-id3-writer`'s `addTag()` calls `removeTag()` and writes only the frames set, and
`writeTrackMetadataToBytes` sets six (and the cover). Checked with the app's own function
(`.tmp/scripts/check-frames.cjs`): a tag with `TIT2 TPOS TPE2 COMM TXXX` (title, disc number, album
artist, a comment, a ReplayGain value) comes out of a title edit as `TIT2 TPE1 TALB`. Lyrics,
MusicBrainz ids, composer, BPM and the like go the same way, silently.

**Proposal (awaiting approval)**: keep every frame not edited: read the existing tag's frames
(the lean reader of 2. can do it) and write them back beside the edited ones, with a test that a
tag with other frames keeps them byte for byte. This should go before FLAC.

### The FLAC risk, spelled out

A FLAC file is `fLaC`, then metadata blocks, then the audio. Each block has a 4-byte header: a
"last block" bit, a type (STREAMINFO, which must come first; PADDING, APPLICATION, SEEKTABLE,
VORBIS_COMMENT, CUESHEET, PICTURE) and a 24-bit length. Tags live in VORBIS_COMMENT (`KEY=value`
pairs with little-endian lengths, while block headers are big-endian), covers in PICTURE blocks.

- **A file that no longer plays**: one wrong length, or the "last block" bit on the wrong block,
  and a decoder no longer finds where the audio starts. Some players fail, others may cope, so it
  can pass a quick check here and fail elsewhere.
- **Silent loss**: rewriting VORBIS_COMMENT with jackbird's six fields deletes the others
  (ALBUMARTIST, DISCNUMBER, REPLAYGAIN_*, MUSICBRAINZ_*, LYRICS…), and dropping unknown blocks
  loses cue sheets or seek tables. Nothing stops playing, so nobody notices until later. (The MP3
  writer above already does the first.)
- **Edges**: a block holds at most 16 MB (a cover larger than that cannot go in); keys repeat (two
  ARTIST values) and are case-insensitive; some files carry a non-standard ID3 tag before `fLaC`;
  files are three to five times larger than MP3, so rewriting one whole when the tags outgrow the
  padding costs memory and time.
- **Not a risk**: a half-written file. The File System Access API writes into a temporary file and
  replaces the original only on `close()`, so a tab closed mid-save leaves the original.
- **Why a writer is worse than a reader**: a reader's bug shows wrong text; a writer's bug changes
  the person's only copy of their files, and they find out later.

Safeguards the FLAC plan would add to the 11:46 one: keep every block and every comment not
edited; write into the padding when the new metadata fits; before writing, parse the new bytes
again and check the structure (STREAMINFO first, exactly one last block, lengths adding up to where
the audio starts) and that the audio bytes are identical to the original's (same hash); refuse to
write otherwise and say why; tests on files encoded and decoded back by `ffmpeg`.

## Extension — 2026-11-04 13:15 — Web Audio's sample rate, vfs-sync's cost; cosmetics: findings and plan

**Summary**: Two questions answered with measurements (does the player set the `AudioContext`'s
sample rate; should the use of vfs-sync be reconsidered), and the plan the owner approved from them,
without the vfs-sync fixes, which the owner, as its maintainer, takes on. Five cosmetic requests
join it.

User messages (translated): *"Are we using AudioContext with sampleRate? About vfs-sync, should we
reconsider its use?"*; then *"OK, go ahead. The vfs-sync fixes are mine, I'm the maintainer.
Cosmetics: the primary (orange) key, better with white text; the selection dialog changes height
each time a tab is chosen, the tabs should always be at the same height; the modals have no
entry/exit animation; in tabs, I'd invert the gradient vertically and put the box-shadow at the
top."*; and *"In `.bank`, I'd raise the padding to .5rem."*

### Findings: the sample rate

- `src/lib/player.ts` makes `new AudioContext()` with no options: it runs at the output device's
  rate (48 kHz mostly, 44.1 kHz on some), with `latencyHint: "interactive"`.
- Setting `sampleRate` would not improve the sound. The `<audio>` element alone is resampled to the
  device's rate; routed through the context it is resampled to the context's rate, the same one by
  default, so it is still one conversion, and the analyser does not change the samples. Forcing
  44100 on a 48 kHz device makes two (file → 44.1 → 48). Following each track's rate is not
  possible: the rate is fixed when the context is made, and an element can be given to one
  `MediaElementAudioSourceNode` in its life, so each change would need a new context and a new
  element, with a gap, and the system's mixer still resamples. Bit-perfect output is E-D8 / E5 of
  `RECORD/2026-08-11.musikmatch-rust-migration.WIP.md`, not this.
- The spectrum does depend on the rate, unseen: `spectrumBands` spreads its bands from bin 0 to the
  last bin, so from 0 Hz to half the context's rate. With 16 bands and `fftSize` 1024:

  | Device | First band | Last band |
  | --- | --- | --- |
  | 44.1 kHz | 0–43 Hz (bin 0 alone: DC) | 14.9–22 kHz |
  | 48 kHz | 0–47 Hz | 16.3–24 kHz |
  | 96 kHz | 0–94 Hz | 32–48 kHz |

  At 48 kHz the last band is above the low-pass of most MP3s (LAME cuts between 16 and 19.5 kHz),
  so it hardly ever lights; at 96 kHz the last two are ultrasound.

### Findings: vfs-sync

What jackbird uses of it: `FSAAdapter` (`pick`, `fromHandle`, `ensurePermission`), `walk`, and the
`VFSAdapter` type. The sync engine is not used (the mesh is deferred, E-D7).

- **Bundle**: about 5 KB minified, 2 KB gzipped. Tree shaking keeps `HandleAdapter`, `FSAAdapter`,
  `walk` and the path helpers; a production build has nothing of `GDriveAdapter`, `sync`, `diff3`
  or `VFSNode`. Not a cost.
- **The walk**, measured in Chromium (Playwright) over OPFS, whose `HandleAdapter` is the one
  `FSAAdapter` extends, with 2,400 MP3s and 200 covers in `Artist/Album/` (three runs each):

  | Walk | Time |
  | --- | --- |
  | `walk()` as it is | 3.3–4.0 s |
  | `walk()` with each entry's `stat` given by the listing | 1.1–1.6 s |
  | The handles' own `getFile()`, folders in parallel | 0.25–0.55 s |

  Two causes: `HandleAdapter.list()` leaves `VFSListEntry.stat` empty (the optional field exists
  for this), so `walk()` calls `stat()` on every file, and each `stat()` resolves the path again
  from the root; and `walk()` visits folders one at a time. jackbird pays it when a root opens and
  on every change of tab (`resyncRootIfNeeded` in `src/lib/roots.ts`). Absolute times on a real
  disk differ; the shape is the same. **The owner fixes both upstream.**
- **Playback**: `VFSAdapter` offers `read()`, a `Uint8Array`, so `load()` in `src/lib/player.ts`
  reads the whole file, copies it (`copy.set`) and the `Blob` copies it again: about three times the
  file in memory for a moment, and nothing sounds until the read is over. From the handle,
  `URL.createObjectURL(await handle.getFile())` holds no bytes, and the browser reads from disk as
  it plays. A 13 MB MP3 bears it; a 24/96 FLAC of 100–200 MB (E3) does not. E4 already plans to
  play from disk without the VFS in Tauri (the asset protocol), so playback wants its own seam.
- **Checked in Chromium for this plan**: an object URL of a `File` from a handle **stalls silently
  once the file is rewritten**: `waiting`, `readyState` 1, no `error` event, and the old `File`
  throws `NotReadableError` when read. (A 36 MB file, rewritten with 4 KB more in front, as a tag
  save does; then a seek to 800 s: stuck at 800.0. Without the rewrite, the same seek plays on.)
  So a save of the playing track, or another program retagging it, would freeze it. The plan
  below reopens the file in both cases.

What vfs-sync gives: one seam (`VFSAdapter`) that E4 implements over Tauri commands and that the
mesh will use. It stays for listing, reading, writing and stat (the scan, tags, `.meta/`).

### Plan

**Audio** (`src/lib/player.ts`, `src/helpers/spectrum.ts`, `src/lib/media.ts`):

1. `new AudioContext({ latencyHint: "playback" })`: the hint meant for music (larger buffers, fewer
   dropouts on slow machines, less CPU). The bars then lead the sound by the output latency (tens
   of milliseconds); checked by eye.
2. `spectrumBands(bins, bands, sampleRate)` spreads the bands logarithmically over a fixed range,
   40 Hz to 16 kHz, whatever the device's rate (each band at least one bin wide, as today, and
   bin 0, DC, left out). `readSpectrum` passes `context.sampleRate`. Tests follow.
3. `src/lib/media.ts` (new): `openMedia(root, relativePath)` gives what the `<audio>` element
   plays, `{ url, release }`: in the browser, the object URL of the `File` its handle gives
   (resolved from `root.rootHandle`), so no bytes are read into memory; E4 adds Tauri's
   `convertFileSrc` there. `load()` uses it; the copies go.
4. The player reopens the playing file, at the same second and playing if it was:
   - when the library's record of the playing track changes (a save, or a change found by the scan
     or the verifier): `NowPlaying` gains the track's checksum, and a change of it with the same
     key reopens instead of loading anew;
   - when it waits for data for more than two seconds while it should play (another program
     rewrote the file and nothing has noticed yet). Once per wait.

**Cosmetics** (`theme/default/`):

5. Key, `primary`: white label. A new token, `--mm-on-accent-key` (`#ffffff` in both tones),
   since `--mm-on-accent` also draws the checkbox's tick and the warning sign's mark, which stay
   dark. White on the accent is 3.4:1 in Silver and 2.9:1 in Graphite (WCAG AA asks 4.5:1 for text
   this size); it is the owner's call, said here so it is on record.
6. Modal: with tabs in its `nav` slot, the dialog keeps one height whichever tab is open (fixed,
   within the viewport; the body scrolls), so the tabs stay in place. The height is measured on
   the Edit tab of a one-track selection, the tallest usual one.
7. Modal: entry and exit animations: the dialog fades in and rises a little, the backdrop fades;
   on close, the reverse. CSS only: `@starting-style` and transitions with `allow-discrete` on
   `display` and `overlay` (Chromium 117+, Safari 17.5+, Firefox 129+; elsewhere it opens and
   closes at once, as today). jq79 scopes `@starting-style` (a `CSSGroupingRule`). With reduced
   motion the durations are 0, so it does not move.
8. Tabs: the bar's gradient inverted (`--mm-chassis` at the top, `--mm-chassis-hi` at the bottom),
   and its inset line at the top instead of the bottom.
9. Key bank (`.bank`): padding `.5rem`.

**Docs**: `STACK.md` (playback from the file; the analyser's range), `docs/usage.md` if a
behaviour it describes changes, the screenshots if the cosmetics change what they show.
