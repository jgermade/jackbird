# iPod sync: the iPod nano and the iPod classic

## 2026-11-14 — The spike's plan: which models, the checksum, the GUID, a first database

**Asked by the owner.** The iPod sync noted on 2026-11-04 (in
[RECORD/2026-11-04.github-actions-workflows.WIP.md](./2026-11-04.github-actions-workflows.WIP.md),
"iPod sync (noted; a topic of its own)") was proposed as a spike with its own record. The owner
gave the go on 2026-11-14 and is mostly interested in the **iPod nano** and the **iPod classic**.
This entry is the plan only. Nothing is built until the owner approves it. The schedule is in
[ROADMAP/2026-11-14/ipod-sync.md](../ROADMAP/2026-11-14/ipod-sync.md).

### What jackbird has today

Nothing for iPods. The only mentions of "iPod" in code are user-agent checks for iOS
(`src/helpers/agent.ts`, `src/lib/platform.ts`, `src/helpers/picked.ts`). The tag crates read and
write MP3 (ID3) and FLAC only. They have no MP4/AAC reader.

### The models in scope

Apple's firmware finds music through a binary database, `iPod_Control/iTunes/iTunesDB`, and not
by scanning folders. From the 3rd-generation nano on, that database also carries a checksum keyed
to the device. The checksum decides what each model costs:

| Model | Years | Mounts as a disk | Database | Checksum | In the spike |
| --- | --- | --- | --- | --- | --- |
| nano 1G, 2G | 2005–06 | yes | `iTunesDB` | none | **yes**: the easy case, a check of the writer alone |
| nano 3G ("fat"), 4G | 2007–08 | yes | `iTunesDB` | `hash58` | **yes** |
| classic 6G, 6.5G, 7G (80/120/160 GB) | 2007–09 | yes | `iTunesDB` | `hash58` | **yes**: the main target |
| nano 5G (camera) | 2009 | yes | `iTunesCDB` (compressed), maybe SQLite as well (to check) | `hash72` | **stretch**, after the rest (I6) |
| nano 6G (square), 7G | 2010, 2012 | yes | SQLite databases and `iTunesCDB` | `hashAB` | **no**: the algorithm is not public |
| iPod video 5G, 5.5G (the classic's predecessor) | 2005–06 | yes | `iTunesDB` | none | free with the above, since the format is the same |

`hash58` is a known algorithm. It is an HMAC-SHA1 over the whole database, with a few header
fields zeroed first, and its key is derived from the device's 8-byte **FireWire GUID** through two
fixed tables. It is described on the iPodLinux wiki and implemented in libgpod. libgpod is LGPL, so
it is a reference for behaviour only: the crate is written from the description, as the tag
crates were (AGENTS.md, "Rust crates").

`hash72` (nano 5G) does not need the GUID. It needs a per-device secret that is pulled out of a
database iTunes wrote once, so that nano has to have been synced by iTunes at least once. It is a
stretch goal, and so is learning whether its firmware also needs the SQLite databases.

### The catches, and how the spike answers each

1. **The GUID.** It is needed for `hash58`.
   - Some iPods write it to `iPod_Control/Device/SysInfo` (`FirewireGuid: 0x…`). Every one returns
     it in `SysInfoExtended`, an XML plist the device sends over a SCSI vendor command. A browser
     cannot send that command.
   - On these models the GUID is also the first 16 hex digits of the device's USB serial number
     (to confirm in I2).
   - **Desktop (Tauri):** the app reads the USB serial or `SysInfoExtended` natively, through sysfs
     on Linux, IOKit on macOS and SetupAPI on Windows.
   - **Web:** the app reads `SysInfo` when the file has the GUID. If it does not, two options are
     tried: WebUSB's `serialNumber` (to check whether Chrome lists a device whose only interface is
     mass storage, a protected class), and as a last resort the person types the serial number
     (shown in Settings › About on the iPod). The GUID is then kept in `iPod_Control/Device/`, as
     libgpod does, so it is asked for once.
2. **The file system.** An iPod formatted on a Mac is HFS+, which Windows and most Linux setups do
   not mount (and a browser sees only what the system mounts). An iPod formatted on Windows is FAT32
   and works everywhere. The spike works with FAT32 and tells the person when it finds HFS+
   (detecting it is part of I2).
3. **The browser and the drive.** Through the File System Access API the person picks the iPod's
   drive like any folder. Two things are checked in I1: that Chrome lets them pick the root of a
   removable drive, and that it lists `iPod_Control`, which is hidden on FAT.
4. **Formats.** The firmware plays MP3, AAC, ALAC, WAV and AIFF, and not FLAC. The spike copies
   MP3s only. AAC and ALAC need an MP4 reader, which the tag crates do not have, and FLAC needs
   converting. Both come later, as steps of their own.
5. **Not breaking the iPod.** The spike never writes over a database it has not read and backed up:
   `iTunesDB` is copied to `iTunesDB.jackbird-backup` first. The new database is written beside it
   and moved into place in one rename. If the iPod does not take the new database, the backup goes
   back into place, and at worst iTunes can restore the device.

### Where the code goes

- **`crates/ipod`** (new). Like the tag crates, it does no I/O. It is handed a database's bytes and
  returns its tracks and playlists, or it is handed a list of tracks and playlists and returns a
  database's bytes. It covers:
  - the `mhbd`, `mhsd`, `mhlt`, `mhit`, `mhod`, `mhlp`, `mhyp`, `mhip` and `mhla` chunks;
  - unknown chunks and fields kept as they were read, so a round trip changes only what jackbird
    changed;
  - `hash58`;
  - telling the model apart from `SysInfo`'s `ModelNumStr` or from the serial number's last
    characters, which decides the checksum.

  It depends on `sha1`, as `crates/core` does. Its tests run on fixtures in `fixtures/ipod/` that a
  script builds: databases made by the crate, plus a real database the owner provides if they want
  to (it holds their library, so it would stay out of the repository unless they say otherwise).
- **Web.** The crate's exports go into `crates/tags-wasm`, or into a module of its own if that one
  grows too much (decided in I3, by the size). The copying goes through the root's existing VFS
  adapter.
- **Desktop.** `crates/core` already opens folders as roots, so the iPod is one of them. `src-tauri`
  adds the GUID command (the USB serial and `SysInfoExtended`).
- **UI.** A small "iPod" panel when the root opened is an iPod: the model, its free space, the
  tracks already on it, a "Send to iPod" action for the selection or a playlist, and "Write the
  database". Every string is in `en.ts` and `es.ts`.

## 2026-11-14 — The nano 7G first: `hashAB` is public now; the plan rebuilt around it

**The owner's answers.** "Classic 5" is the iPod video (5G). The owner wants to **start with the
iPod nano 7G**.

**What changed since the first plan.** The first plan (and the 2026-11-04 note) treated `hashAB`
as not public. That is out of date. A search on 2026-11-14 found:

- **[dstaley/hashab](https://github.com/dstaley/hashab)**: a C implementation of `hashAB`,
  reverse engineered from a decrypted nano 6G firmware and checked against the old closed
  `libhashab32.so` on 10,000 random inputs.
  - Licence: the Unlicense (public domain). Its EDON-R file is RHash's, under a permissive
    "use, copy, modify for any purpose" licence. Neither is GPL or LGPL.
  - Input: a 20-byte SHA-1 and the device's 8-byte FireWire GUID. Output: a 57-byte signature.
  - It ships 100 test vectors (`test-data.json`) and a WebAssembly build.
- **[SyncMyPod](https://github.com/toofunky/SyncMyPod)** (MIT, macOS, Swift). Its PR #12 (merged
  2026-09-30) syncs songs, playlists, artwork and play counts to a real nano 7G. Its Swift port of
  `hashAB` passes dstaley's 100 vectors and validates a signature that iTunes wrote on a real nano
  7G. It is taken as a reference for behaviour only, as libgpod is.
- **[iOpenPod](https://github.com/TheRealSavi/iOpenPod)** (GPL-3.0) lists the nano 1G–7G as
  targets and uses dstaley's WebAssembly build. Being GPL, it is not looked at beyond its README.

**What the nano 7G needs.** This comes from SyncMyPod's PR and code, read in the session's scratch
folder only and not copied into the repository. Each point is to be checked on the owner's device
in N1–N3.

- **Detection:** the model number in `SysInfo`, or the USB product ID `0x1267` when `SysInfo` is
  empty.
- **`iPod_Control/iTunes/iTunesCDB`:** an `mhbd` header left uncompressed (the compression flag is
  at `0xA8`), followed by the rest of an `iTunesDB` as one zlib stream. So the chunk reader is the
  same as the classic's.
- **The signature:** scheme `3` at offset `0x30`, and a 57-byte `hashAB` at `0xAB..0xE4`. It is
  computed over the SHA-1 of the file with `0x18..0x20`, `0x58..0x6C`, `0x72..0xA0` and the
  signature itself zeroed, plus the FireWire GUID and 23 random bytes, which the signature carries
  in the clear.
- **The SQLite library:** `iPod_Control/iTunes/iTunes Library.itlp/`, made of `Library.itdb`,
  `Locations.itdb`, `Dynamic.itdb` and others. It is built as iTunes builds it: the base tables
  first, then the post-process SQL that the nano itself provides in `SysInfoExtended`.
- **`Locations.itdb.cbk`:** the SHA-1 of each 1 KB block of `Locations.itdb`, the SHA-1 of those
  digests, and a `hashAB` signature over that last digest.
- **Rows the nano owns** are carried over from its current files: play counts and statistics in
  `Dynamic.itdb`, and its own view state. The `Play Counts` file is used and then discarded, so
  plays are not counted twice.
- **`SysInfoExtended`** holds both the GUID and the post-process SQL. The nano returns it over a
  SCSI INQUIRY (vendor pages) and does not keep it as a file. **A browser cannot read it.**

### What this means for jackbird

1. **The desktop app writes to a nano 7G, and the web reads it.**
   - Reading the `iTunesCDB` needs only zlib, which works in WebAssembly.
   - Writing needs `SysInfoExtended`, which a browser cannot read, and SQLite. Building SQLite for
     the web's WebAssembly is a project of its own.
   - Once the desktop app has read `SysInfoExtended`, it keeps a copy at
     `iPod_Control/Device/SysInfoExtended`, as libgpod does. A later step could then let the web
     write too, without the hardware query (not in the spike).
2. **Reading `SysInfoExtended` from the desktop app** is a SCSI INQUIRY on the device:
   - On Linux this is an `SG_IO` ioctl. That is **unsafe code**, which the workspace forbids
     outside the approved blocks (AGENTS.md, "Rust crates").
   - On macOS it goes through IOKit, and on Windows through `IOCTL_SCSI_PASS_THROUGH`, both FFI.
   - Proposed for the spike, so that no unsafe code is needed: the desktop app runs a system tool
     that already does this, `sg_inq` from sg3_utils on Linux. Failing that, the owner reads it
     once with any tool, and jackbird reads the copy at `iPod_Control/Device/SysInfoExtended`. A
     native read, with its unsafe block per system, is a later decision for the owner.
3. **`hashAB` in Rust.** It is ported from dstaley's C (public domain) into a module of
   `crates/ipod`, credited in a header comment the way SyncMyPod credits it, and tested with
   dstaley's 100 vectors (`test-data.json` copied into `fixtures/ipod/`, which its licence allows).
   AGENTS.md says crates are written from the formats' specifications. `hashAB` has no
   specification: the public-domain C is the description. **Porting it needs the owner's approval**
   (asked below).
4. **New dependencies** (each needs approval):
   - `miniz_oxide` in `crates/ipod`: pure Rust, MIT/Apache-2.0/Zlib, for the `iTunesCDB`'s zlib.
   - `rusqlite` with `bundled`, already used by `crates/store` and `crates/service`, for the SQLite
     library. `crates/ipod` stays free of I/O: it builds the databases in memory and returns their
     bytes (rusqlite's `serialize`, to confirm), and `crates/core` writes them.
5. **Formats on the nano 7G:** MP3 and AAC, not FLAC. The spike copies MP3s, as planned.
