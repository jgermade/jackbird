# Releases and deployment

Three GitHub Actions workflows, in [`.github/workflows/`](../.github/workflows/), build, release
and deploy jackbird. Deployment goes to GitHub Pages: a landing page at
<https://jgermade.github.io/jackbird/>, and the app's demo at <https://jgermade.github.io/jackbird/demo/>.

## `build.yml`: test and bundle

Runs on every push to `main`, on every pull request, and by hand. It installs the dependencies
with `npm ci`, runs `npm test`, builds with `npm run build`, and uploads `dist/` as the `dist`
artifact of the run.

## `release.yml`: cut a release

Run it by hand from **Actions → release → Run workflow**, on `main`, with two inputs:

| Input | Values | Default |
| --- | --- | --- |
| `bump` | `patch`, `minor`, `major` | `patch` |
| `deploy` | checkbox | unticked |

It then:

1. **Bumps the version** with `npm version <bump>`: `package.json` and `package-lock.json` change,
   and the commit `chore(release): X.Y.Z` and the tag `vX.Y.Z` are pushed to `main` together.
2. **Builds the tag** by running `build.yml` on it.
3. **Publishes the release** `vX.Y.Z` with notes generated by GitHub, and the build attached as
   `jackbird-vX.Y.Z.zip`.
4. **Deploys it**, if `deploy` was ticked, by running `deploy.yml` on the new tag.

Only one release runs at a time. If the build fails, the tag stays without a release: fix the
cause and release again (which makes the next version), and delete the empty tag by hand if you
want.

## `phone-release.yml`: the Android app

`release.yml` calls it, and the release carries its APK: `jackbird-vX.Y.Z-android.apk`, one APK
for phones (arm64, armv7) and emulators (x86_64). It also runs by hand (**Actions → phone-release
→ Run workflow**, on any branch) and on pushes that change the phone's app, with the APK as the
run's `phone-apk` artifact, to try it before a release.

Android installs an update over an app only if both are signed with the same key, so the APK is
signed with a keystore kept in the repository's secrets (**Settings → Secrets and variables →
Actions**):

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE` | the keystore file, in base64 (`base64 -w0 jackbird-release.jks`) |
| `ANDROID_KEYSTORE_PASSWORD` | its password |
| `ANDROID_KEY_ALIAS` | the key's alias (`jackbird`) |
| `ANDROID_KEY_PASSWORD` | the key's password (the same one, for a PKCS12 keystore) |

It is made once, with a JDK's `keytool`:

```sh
keytool -genkeypair -v -keystore jackbird-release.jks -alias jackbird \
  -keyalg RSA -keysize 4096 -validity 36500 -storetype PKCS12
```

Keep the file and its password somewhere safe besides GitHub: a secret cannot be read back, and
without the key, the next APK installs only after the app is removed. Without the secrets, the APK
is signed with a key made for that run and named `…-android-testkey.apk`.

## `deploy.yml`: deploy a release

Run it by hand from **Actions → deploy → Run workflow**, with one input:

| Input | Values | Default |
| --- | --- | --- |
| `tag` | a release tag, such as `v0.2.0`, or `latest` | `latest` |

It publishes three things to GitHub Pages:

- **The landing page**, at the root (<https://jgermade.github.io/jackbird/>): `landing/`, put
  together by `node scripts/build-landing.mjs site` from the commit the workflow runs on, with the
  Deck theme's tokens and fonts, the logo and the screenshots it borrows. To look at it locally,
  run `node scripts/build-landing.mjs` and serve `.tmp/landing/`.
- **The app, as the demo**, at `/demo/`. It does not rebuild it: it downloads the zip attached to
  that release (for `latest`, the latest release), so what goes live is exactly what was tested
  and released.
- **The design system**, at `/design/`: a redirect to the Deck theme's specimen sheet, which
  every build carries (`/demo/theme/default/`).

Deploying an older tag rolls the demo back to it; the landing page is always the workflow's own.
Deployments run one at a time, in the `github-pages` environment, and the run links to the
published site.

The build uses a relative base (`base: "./"` in `vite.config.ts`), so the same files work under
`/jackbird/demo/` on Pages and at the root anywhere else.

## One-off settings on GitHub

- **Settings → Pages → Build and deployment → Source: GitHub Actions.** Until then, `deploy.yml`
  fails: the workflow cannot turn Pages on by itself.
- **Pushes from `github-actions[bot]` to `main`.** A release pushes its version commit and tag
  with the workflow's token. If `main` gets a branch protection rule or a ruleset that requires
  pull requests, allow the bot to bypass it, or the release stops at its first step.

## Why the workflows call each other

Pushes and releases made with a workflow's token start no other workflow. So the version commit
does not trigger a second build on `main`, and `release.yml` runs `build.yml` and `deploy.yml`
itself instead of waiting for them to react.
